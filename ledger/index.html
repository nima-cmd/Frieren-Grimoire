Front matter

How to read this

Claims about hardware carry their epistemic status, the same convention as NOTES.md:

  • [V] — verified on this machine, or read out of named source code.
  • [R] — reported by a secondary source; reliability noted.
  • [?] — assumed, inferred or predicted. Not verified. Do not build on it.

The distinction matters because a clean derivation from a half-remembered fact is exactly as convincing as a correct one. Chapter V exists because that happened twice on the first night.

Chapter I

Speaking to devices

hidraw

A raw channel to a USB HID device, at /dev/hidrawN. "Raw" means the kernel hands bytes straight through instead of interpreting them as mouse movement or keypresses. It is how you say things a mouse driver has no vocabulary for — change your DPI, what is your battery level.

sysfs and uevent

/sys is a fake filesystem the kernel generates to describe its own state. Nothing there is on disk. Every hidraw node has a matching directory, and inside it device/uevent names the hardware:

HID_ID=0003:00001532:0000007E
HID_NAME=RAZER Razer Mouse Dock

HID_ID is bus : vendor : product in hex. Matching on it is how discovery works.

vid / pid

Vendor ID and product ID — the two numbers that identify a USB device model. Razer is 1532, Logitech 046d, ASUS 0b05. The DeathAdder V2 Pro is 1532:007d. [V]

Gotcha — node numbers are not stable. Observed twice in one session on this machine, nothing unplugged in between: 
first read   DeathAdder → hidraw12,13,14,17,19   Dock → hidraw15,16,18
later read   Dock       → hidraw12,13,14         DeathAdder → hidraw15,16,17,18,19
The wireless mouse slept and re-enumerated, and the two swapped ranges. Code holding hidraw12 would now be sending mouse commands to the dock. Always discover by vid/pid; never remember a path.

udev and uaccess

udev reacts to devices appearing and can set permissions on their nodes. By default /dev/hidraw* is root-only, which is why a rule is needed. TAG+="uaccess" asks systemd-logind to grant an ACL to whoever is logged in at the seat — more modern than adding yourself to a group, and it follows the session.

Gotcha — OpenRazer never touches hidraw permissions. [V] Its 99-razer.rules only covers usb/input/hid nodes and the sysfs attribute directory; a grep of the whole repo finds zero references to hidraw. It works through sysfs files the kernel driver creates. That is why the Razer hidraw nodes are still root-only here even though the daemon is fine.

evdev and uinput

Two halves of the same door. evdev reads input events and can tell you which device a key came from. uinput creates a virtual keyboard or mouse and injects events. Both work under Wayland, because they sit in the kernel below the display server — which is why `xdotool` fails on COSMIC and uinput does not.

DKMS

Dynamic Kernel Module Support — rebuilds an out-of-tree kernel module automatically whenever the kernel updates. OpenRazer ships its driver this way.

Chapter II

The Razer Chroma protocol

feature report

USB HID carries three kinds of traffic. Input reports flow device→host (you moved the mouse). Output reports flow host→device. A feature report is a two-way control channel for configuration — you set it, and you can read it back. Razer's whole protocol rides on feature report ID 0x00.

The 90-byte report

[V] From razercommon.h, with a static_assert that the struct is exactly 90 bytes:

OffsetField
0status
1transaction_id
2–3remaining_packets (big-endian)
4protocol_type
5data_size
6command_class
7command_id
8–87arguments[80]
88crc
89reserved

transaction ID

A per-device-model tag that must be correct or the device silently ignores you. It is not a sequence number and does not increment. [V] The DeathAdder V2 Pro (007d) uses 0x3f.

CRC

A checksum proving the frame arrived intact. Razer's is deliberately simple — [V] razercommon.c:111-119 XORs bytes 2 through 87 inclusive and stores the result at byte 88.

Why XOR? It is one instruction per byte and catches any single-byte corruption. It would miss two errors that cancel out, which over a 10 cm USB cable is an acceptable trade.

Worth knowing: charge_level reads 245. That is not 245% — the value is raw 0–255, so it is ≈96%. [V] confirmed in razerchromacommon.c:1057-1060, where the driver hands back arguments[1] for the caller to scale.

Chapter III

Keys, chords and events

The vocabulary here is small, and the gap between the last two rows is where a real bug lived for months.

TermExampleMeaning
keyRightone physical key
modifierCtrl, Alt changes another key's meaning while held
chordCtrl+Alt+Right modifiers + one key, pressed together. One action.
key eventctrl↓ a single down or up. What the kernel consumes.
macroCtrl+C, wait, Ctrl+V an ordered list of chords

"Chord" is borrowed from music: notes struck together rather than in sequence. One chord is several key events — Ctrl+Alt+Right is one chord and six events:

ctrl↓  alt↓  right↓  right↑  alt↑  ctrl↑

Chords nest like brackets

Release in the reverse order you pressed. Ctrl( Alt( Right ) ). Compare a correct macro with a broken one from the live deck config: [V]

Copy                ctrl↓  c↓      c↑  ctrl↑     correct
Duplicate Keyframe  ctrl↓  d↓   ctrl↑     d↑     crossed brackets
Start Pause         ctrl↓  space↓  space↑         ctrl never released
Gotcha — a leaked modifier is invisible and lasts. Because injection happens at kernel level, an unreleased Ctrl stays held system-wide. In Krita, held Ctrl is the colour picker, so the next pen stroke samples colour instead of drawing. The symptom appears minutes later, in a different app, with no error — which is why it survived so long.
Question asked: "what is the chord and is macros.json part of our app now"

A chord is the combination you mean; key events are what the kernel needs. And no — ~/.config/LoupixDeck/macros.json belongs to LoupixDeck. It matters to us twice, read-only both times: as a test fixture (it holds three known bugs, so it is the answer key for the validator) and later as a one-time import. Never written to — LoupixDeck rewrites it on exit and would clobber us.

Chapter IV

Configuration that cannot be wrong

imperative vs declarative

An imperative config lists the steps: press ctrl, press space, release space, release ctrl. A declarative one states the intent: Ctrl+Space — and the program derives the steps.

LoupixDeck is imperative, and three of its five hand-built macros have ordering faults. The two that are correct shipped as presets. That is not carelessness; it is a data model whose most likely outcome is a bug.

The principle: make the bug unrepresentable rather than asking the user to be careful. If a chord is written "Ctrl+Space" and the app expands it, you cannot leak a modifier — there is no way to write down a half-open chord.

Bind the action, not the keystroke

Weaker: {"keys": "Ctrl+Alt+Right"}. Stronger: {"krita": "next_frame"}, resolved against Krita's own kritashortcutsrc at runtime.

Why it is stronger: rebinding in Krita no longer breaks the deck, dead bindings become detectable, and the keystroke cannot drift out of sync — because there is only one place holding it. The deck's dead scrub knob (Ctrl+Shift+Right vs Krita's Ctrl+Alt+Right) is exactly that drift, and could not have happened under this model.

Errata

Mistakes, kept on purpose

Recorded next to the correction, because the failure is usually the more useful half.

1. The transaction ID that would have silently failed

Claimed: 0x1F, carried over from the macOS notes.
Actually: 0x3f for the DeathAdder V2 Pro. [V] confirmed at four separate sites in razermouse_driver.c.

Why it mattered: 0x1F is genuinely correct — for the BlackWidow Elite, a keyboard not attached to this machine. A clean derivation from a correct- but-irrelevant fact produces silent no-ops that look exactly like a wiring fault.

2. "Removing OpenRazer is painful"

Claimed: painful, in a table of removal steps.
Actually: one apt remove, four packages, no cascade. The PPA stays configured and it is also in Pop's own universe repo. [V] confirmed with apt-get -s.

The real cost is timing, not difficulty — while the direct-hidraw code is being validated, OpenRazer's sysfs is free ground truth. Removing it early throws away the answer key.

3. Trusting date without asking whether it was right

Claimed: the session began 6:33pm Tue 20 Oct and ran "about three hours", with the hidraw renumbering timed at 18:35 and 21:35.
Actually: the system clock was wrong by roughly two days. It read Tue Oct 20 all evening and then jumped to Thu Oct 22 17:23 PDT when NTP corrected it (timedatectl: System clock synchronized: yes). Every date written into this repo was wrong, and every elapsed-time claim was a difference between two readings of a drifting clock.

The lesson, and it generalises past clocks. The standing rule was never guess the clock — run date, and that rule was followed every single time. It still produced two days of wrong dates, because running the command only replaces your guess with the machine's claim. A measurement is not the same as a verified measurement.

What would have caught it instantly: the session context said "Today's date is 2026-10-22" from the very first message, and date said the 20th. Two sources disagreed and the conflict went unnoticed for the whole session. Cross-check the instrument against a second source before building numbers on it.

Note what survived: the hidraw renumbering is a direct observation — hidraw12 named one device, then named another — and needs no clock at all. Observations outlive the instruments that timestamp them, which is a good reason to record what you saw separately from when you saw it.

4. The mitigation that does not work here

Standard advice for OpenRGB is "don't load i2c-dev/i2c-piix4." [V] On this machine i2c-dev is compiled into the kernel and i2c_piix4 is already loaded, with three live SMBus adapters. Withholding modules protects nothing; only OpenRGB's own setting does.
